**Implements:** FR-3 rows R9 (Trigger a cloud flow) and R10 (Call a Dataverse custom API), the R9 and R10 rows of the recipe contract table and example requests, and the shared Musts they touch (validation before any call, missing-setting fail-closed F57, logging rule F09, `toResult`, GUID, return shape, Body decoding F01) | **Satisfies:** AC-3.2 (zero FR-4 hits for R9 and R10), AC-3.3 and AC-3.10 (header comment links the Learn page), AC-3.5 (`CLOUD_FLOW_ID` read through `Server.SiteSetting.Get`, never a literal), AC-3.6 (the handler side of the permission data), AC-4.2 (highlight lines), F07 (placeholder names and prerequisites visible in the handler), F01, F09; Learn corrections 7 (R9 `async`), 11 (`toResult`, status check, `Body` decoding), 14 (no restricted text), 19 (R10 never awaits Dataverse), 20 (`StatusCode` 0 is caught by the status check), 22 (top-level helpers)
**Depends on:** 02 (`runBrowserChecks`), 05 (`getRecipe`, `snippets.ts`)
**Files:**
- Replace the Phase 00 stubs: `src/services/generators/handlers/r9.ts`, `src/services/generators/handlers/r10.ts`.
- Create tests: `src/services/generators/handlers/r9.test.ts`, `src/services/generators/handlers/r10.test.ts`, `src/services/generators/handlers/r9r10.catalogue.test.ts`.

**Interfaces:**
- **Consumes** (exact names): `GeneratedHandler`, `RecipeMeta` from `@/types/recipe`; `METHOD_FUNCTION` from `@/types/http`; `getRecipe` from `@/services/catalogue/recipes`; from `snippets.ts`: `TO_RESULT`, `IS_GUID`, `headerComment`, `requireSettingsCode`, `failureReturn`, `validationFailureReturn`, `validationFailureReturnFor`, `logLine`. Test-only: `runBrowserChecks` (`@/lib/code-analysis/browserChecks`), `exportedFunctionNames` and `usedServerMembers` (`@/lib/code-analysis/structure`), `generateHandler` (`./index`).
- **Produces** (signatures unchanged from the stubs): `generateR9(): GeneratedHandler` and `generateR10(): GeneratedHandler`. No new exports. Later phases read them only through `generateHandler('R9')` and `generateHandler('R10')`.

The phase replaces two throwing stubs with pure, deterministic generators for the two reference-sample recipes. R9 is an `async post` that validates the request body, fails closed when `CLOUD_FLOW_ID` is missing, calls `Server.Connector.CloudFlow.TriggerAsync(flowId, payload)` and returns the flow's `Body` decoded as JSON-or-text (F01). R10 is a synchronous trio, `get` (bound function), `post` (unbound action) and `patch` (bound action called with `"post"`), over `Server.Connector.Dataverse.InvokeCustomApi(httpMethod, url, payload)`, with GUID-checked `id` and placeholder API names the maker replaces (F07). Each generator is written golden-first: the expected text is hand-authored from the spec, committed, then matched byte for byte.

## Decisions

1. **Golden files** live at `src/services/generators/handlers/__golden__/<id>.js.txt` with the recipe id in capitals (`R9.js.txt`, `R10.js.txt`). They are hand-written from the spec, never generated, and committed before the generator (red first). Tests read them with `readFileSync` and compare with `toBe`. No `toMatchFileSnapshot`, no `-u`. The `.txt` suffix keeps ESLint, Prettier and `tsc` off them. The file bytes are the handler text exactly, ending with one LF; the orchestrator should confirm the other B1 phases use the same ending (open question 1).
2. **Generators are pure**: no clock, no randomness, LF only, literals built with `JSON.stringify` (placeholder API names, entity set, messages, the Learn URL inside `headerComment`). The entity set `accounts` comes from `getRecipe('R10').tables[0]` so the handler and the checklist cannot drift; the three API names are generator constants.
3. **R9 flow order**: header comment, `toResult`, then in `post`: parse and validate the body (a non-null, non-array JSON object, else `errors: [{ field: "body", message }]` through `validationFailureReturn`), then `requireSettingsCode(["CLOUD_FLOW_ID"], …)` (variable `cloudFlowId`), then `await TriggerAsync(cloudFlowId, JSON.stringify(payload))`. Validation comes before the setting read so that no request is sent to the flow, and no configuration hint is returned, for a request that is invalid anyway. `CLOUD_FLOW_ID` is not GUID-checked: the spec asks only for fail-closed on missing or empty.
4. **R9 payload** is the validated object re-serialised with `JSON.stringify`, never the raw `Body` text. Learn adds `siteId`, `siteUrl` and `userId` to the flow payload itself, so the handler adds nothing. Keys are passed through unfiltered because flow trigger input names are the maker's (open question 2).
5. **R9 result handling**: `toResult(await …)`, then `IsSuccessStatusCode` false logs `Server.Logger.Error("R9 trigger" + " " + r.StatusCode + " " + r.ReasonPhrase)` through `logLine` and returns the fixed message "Couldn't trigger the flow." Success returns `{ status: "success", flowResponse }`. `flowResponse` is `null` for an empty or absent `Body` (so a `202` is success with `null`), otherwise `JSON.parse(Body)` and, if that throws, the raw string unchanged. The fallback is the one place a parse failure is not an error (F01, FR-3 "Only R9 tries JSON and falls back to text"). `CloudFlow` results have no `Headers`, so none is read. A blocked or failed call with `StatusCode` 0 takes the same failure branch (correction 20).
6. **R9 is `async`; R10 is not** (corrections 7 and 19). `post` awaits `TriggerAsync` and nothing else. No R10 function is `async` and none awaits `InvokeCustomApi`.
7. **Exceptions**: each handler function wraps its connector call and result handling in `try`/`catch`. The catch logs `logLine({ fields: ['exception'] })` (operation name plus `e.name`) and returns the recipe's fixed failure message. No `Body`, `e.message`, URL, header, flow ID or payload is ever logged or returned (F09). `ActivityId` is not logged here; the README points to `x-ms-user-trace` for diagnostics.
8. **R10 structure**: three placeholder constants (`new_CustomBoundFunction`, `new_Action`, `new_CustomBoundAction`) with a plain comment line telling the maker to replace them and to review what each API changes beyond the bound record (F07, wording free of restricted words). Two file-private helpers sit above the handlers: `parseJsonObject` (parse of `Server.Context.Body`, returns an object or `null`) and `respond(operation, raw)` (`toResult`, status check, `Body` decoding, success or failure return). Top-level helpers are accepted at runtime (correction 22). `respond` takes the raw connector value so the three `InvokeCustomApi(...)` calls stay inline in `get`, `post` and `patch`, and those three lines are the highlight lines.
9. **R10 validation** collects errors into an array and returns `validationFailureReturnFor` before any `InvokeCustomApi` call. `get` and `patch` require `id` from `Server.Context.QueryParameters` and check `isGuid`; the field is `"id"`, with the messages "id is required." and "id must be a GUID.". `post` and `patch` require a body that parses to an object (field `"body"`, "Body must be a JSON object."). `post` does not read `id`, so a stray `id` is ignored, not rejected. `get` reads no body. A bound URL is `accounts(<id>)/Microsoft.Dynamics.CRM.<name>`, built only from the checked GUID and the constants.
10. **R10 calls**: `get` uses `"get"`; `post` uses `"post"` with the unbound name and `JSON.stringify(body)`; `patch` uses `"post"` with the bound-action URL and `JSON.stringify(body)` (the bound action changes the bound record; Learn shows `"post"` for bound actions). The success payload is `{ status: "success", data }` where `data` is the decoded `Body` or `null` when empty (a `204` is `null`). A non-empty `Body` that fails `JSON.parse` is a caught error and returns the failure.
11. **Highlight lines** (AC-4.2, "the lines that do the recipe's data access"): R9 highlights the single `TriggerAsync` call line; R10 highlights the three `InvokeCustomApi` call lines, ascending. Tests assert the literal numbers and that each such line contains the call text.
12. **Static checks only; behaviour is Phase 17's.** Product code and this phase's tests never evaluate generated code. Only the AC-4.12 harness runs it in `node:vm`. This phase proves text, structure, logging rule and FR-4 cleanliness; a logic slip in a golden would surface in Phase 17 (open question 3).
13. **Wording rules** for all emitted text: arrow functions only (no anonymous `function (`), no `delete`, `prototype`, `fetch`, `window`, `document` or other FR-4 words in comments or strings (correction 14), and a comment never puts a parenthesis right after a restricted name. `runBrowserChecks` is the oracle.

## Risks and open questions
1. **Golden line endings and trailing newline.** Decision 1 assumes one trailing LF. If another B1 phase picked otherwise, align before merge (orchestrator).
2. **R9 payload keys are unfiltered.** The validated object goes to the flow as is, because the flow's trigger input names are the maker's. Validation is not authorization; the README (Phase 14) should say the flow must validate its own inputs. No allowlist is added without a spec change.
3. **No behaviour test in this phase** (Decision 12). If Phase 17 finds a logic slip, the golden changes there. Owner may allow a small `node:vm` smoke test here instead; it would duplicate Phase 17's helper.
4. **`CloudFlow.TriggerAsync` has never run on a live site** (S4 item 6). The call form and the "response envelope without `Headers`" come from Learn only. `toResult` tolerates a string or an object, but whether `Body` is always a string for a flow with a Response action is unverified.
5. **R10 `ExecutePrivilegeName` identity is unverified** (S4 item 6, F07). The handler cannot resolve it; the checklist's "maker verifies" line stands. Placeholder APIs will return 404 or 400 until replaced, which the handler reports as the fixed failure message.
6. **`Server.Context.QueryParameters.id`** access is assumed from Learn's tutorial style; S4 did not probe it. Phase 17 and the first live run confirm.
7. **Duplicate `parseJsonObject` helper** appears in R9, R10 and likely other recipes because `snippets.ts` (Phase 05) has no shared one and this phase may not edit it. Hoisting is a later cleanup that would regenerate every golden.
